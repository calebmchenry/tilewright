## Outcome

Let authors choose map dimensions and deliberately add space without automatic expansion.

## Source and scope

**Source:** INTENT.md — Map size and navigation; INTENT.md — First-version success criteria; INTENT.md — Remaining implementation decisions.

**Execution order:** 12 of 54. Phase: canvas.

performance findings are deferred to TW-049/TW-050 and do not block this ticket.

## Work

- Implement New Map dimensions and documented defaults with validation and tile/chunk size feedback.
- Implement explicit growth controls using the established direction/increment policy and coordinate convention.
- Route growth through history and update camera limits, grids, and overview caches.

## Acceptance criteria

- [x] Valid maps can be created at small, non-chunk-aligned, and approximately 6,400 by 6,400 dimensions.
- [x] Invalid/unsafe dimensions are explained without allocating an accidental huge dense canvas.
- [x] Growth preserves existing layers, registry associations, and annotation positions according to the coordinate contract; new space is empty.
- [x] Painting/dragging outside bounds never grows the map; growth undo/redo restores bounds and content consistently.

## Validation

- Test dimensions, every supported growth direction, coordinate stability, boundary edits, and undo/redo.
- Grow a populated multilayer fixture and confirm its original content still renders at the expected positions.

Record the implementation/decision location and actual validation evidence in this ticket before marking it done.

Acceptance evidence:

- Creation passes for 1×1, 101×130, default 256×256, 6,400×6,400 and the
  65,536×65,536 authoring maximum. Domain assertions show zero allocated tile
  partitions and zero typed-array tile bytes. Browser flows create small,
  partial-chunk and target-size maps with one fresh layer and no prior history.
- Invalid/unsafe inputs fail before construction or command execution. Blank,
  zero/negative, fractional, exponential, unsafe integer, overflowing and oversized
  values have explanations; invalid replacement preserves the original session.
  Chosen guardrail: 65,536 tiles (1,024 chunks) per axis, documented as an
  implementation limit rather than a performance guarantee. The low-level model's
  safe-integer coordinate contract remains unchanged.
- Each left/right/top/bottom direction and combined counts preserve all runs,
  ordered layer identities/names, registered associations, registry records,
  annotation bounds/anchors, storage statistics and viewport. Added space is empty
  on every layer. Tests use the populated 196×198 two-layer grid fixture, including
  an 8×8 footprint across four visual chunks. Growth does not snap partial edges.
- Actual WebGL samples at DPR 1 and 2 preserve building/terrain pixels at their
  original world coordinates in detail and overview. Growth releases/rebuilds
  overview images; added-space pixels become empty map background, and undo
  restores outside-map clipping. Undo and redo follow the same bounds notifications.
- Boundary writes and out-of-map tool picking cannot grow bounds; an Inspect drag
  outside the canvas/map leaves size and redo intact. Painting tools themselves
  remain later tickets; this validates their existing bounded command/input seams.
  Tests paint into newly grown negative space, undo that paint, undo growth, then
  redo both, restoring original and new-space content without data loss.
- Camera position/zoom stay fixed on growth. Tests prove subsequent pan/zoom limits
  use current bounds; grid, dimension and overview updates reuse the established
  bounds invalidation route. New Map disposes old canvases/GPU contexts and resets
  panel drafts under Strict Mode.
