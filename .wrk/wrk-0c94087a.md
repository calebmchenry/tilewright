## Outcome

Recover recent committed browser work after reload/crash without confusing local
browser recovery with a downloaded project file.

## Source and scope

Read docs/recovery-policy.md, src/editor/recovery.ts,
src/editor/recovery-discovery.ts and src/RecoveryPanel.tsx. Adapt the existing
snapshot/validation/review contracts rather than duplicating the project format.
Native source-file reread and filesystem identity checks are not browser promises.

## Work and acceptance criteria

- [x] Store versioned, validated recovery payloads and metadata in IndexedDB with
  transactional publication, bounded retention and coalesced checkpoint cadence.
  Store committed snapshots; never capture transient gestures or half-written state.
- [x] Discover and review checkpoints on startup; restore as an independent
  unsaved copy and allow deliberate discard. A corrupt checkpoint must not
  replace the current document or prevent review of other valid entries.
- [x] Handle blocked database upgrades, unavailable storage, quota exhaustion and
  failed transactions with useful feedback while keeping editing and downloads
  available. Do not claim persistence when storage fails.
- [x] Isolate concurrent tabs/writers so one tab cannot overwrite or discard
  another tab's active work. Handle stale asynchronous jobs and session changes.
- [x] Download requests do not delete recovery as though a durable save succeeded.
  Define and test retention/resolution on New/Open/discard/restore; browser shutdown
  must not be the only opportunity to checkpoint.
- [x] Document origin-specific storage, clearing/eviction/private-mode limitations,
  and that downloaded project files remain the durable user-owned copies.
- [x] Preserve the existing desktop recovery behavior and metadata semantics.

## Validation

Use isolated browser contexts to test edit/checkpoint/reload/restore, interrupted
publication, invalid data, discard, failed storage, version upgrade and multiple
tabs. Verify restored full project semantics and continued export/download after
storage errors. Run recovery domain and desktop adapter regressions.

### Phase 1 — transactional browser storage

- src/platform/browser-recovery.ts implements the existing RecoveryBridge and
  RecoveryReviewBridge using IndexedDB and Web Locks. It reuses the complete
  .tilewright decoder, version-1 recovery metadata, SHA-256 integrity checks and
  shared committed-snapshot encoder. Browser SavedContext and savedRevision are
  always null; imported display names never grant source-file access.
- Database schema version 2 has separate lineage metadata and payload stores.
  The tested v1-to-v2 upgrade adds a lineage cleanup index without altering data.
  Unknown database versions remain untouched. Version-change handlers close old
  connections, blocked opens surface actionable feedback, and retries share the
  blocked result until the abandoned open request can terminate. This avoids a
  second request waiting silently behind the first blocked upgrade.
- Prepare clones and fully validates bytes in private memory. Commit checks the
  live writer/epoch and sequence, then publishes payload, metadata, next sequence
  and retention changes in one transaction. Only transaction completion permits
  acknowledgement. Quota errors, aborts and stale jobs preserve prior checkpoints.
  Exhausted or corrupted sequence counters cannot publish invalid records.
- Retention is two generations per lineage, ten unresolved lineages per origin,
  and a 1 GiB logical retained-byte ceiling with a 64 KiB bookkeeping allowance.
  The previous valid fallback is preferred if the latest generation is corrupt.
  No age-based deletion or eviction of another unresolved map occurs. One private
  prepared payload per tab is additional; browser quota and physical overhead can
  impose smaller limits. Selected cleanup deletes both stores transactionally.
- Exclusive per-lineage Web Locks protect active/suspended tabs without leases.
  Different tabs and separate openings receive independent identities. Claims and
  discard recheck ownership at action time. Disposal aborts transactions still before commit, clears
  pending bytes, releases locks and closes the database; process/tab termination
  releases browser-owned locks. Stale epochs and session changes cannot acknowledge
  or replace another session's data.

### Phase 2 — shared lifecycle, review and browser feedback

- src/platform/browser.ts and select.ts construct a fresh browser service/adapter
  per application. Existing shared application composition starts the coordinator
  and startup review. No native module/IPC, backend, account or cloud storage is
  introduced. The existing coordinator retains 2-second trailing debounce,
  10-second maximum scheduling delay and 5-second minimum capture spacing; it
  captures only committed state and coalesces later edits into one request.
- src/editor/recovery.ts adds optional adapter release/disposal hooks, ordered
  behind existing publication work. Desktop adapters have no new behavior.
  src/editor/project-files.ts now resolves browser Open's outgoing recovery only
  after complete candidate validation and the final transition check, under the
  existing brief edit gate. New and restore reuse their existing guarded path.
  Failed/canceled/invalid transitions retain the outgoing workspace and checkpoint.
- Downloads and agent exports never resolve recovery, mark saved or fabricate a
  native receipt. Reload/close retain completed checkpoints; shutdown is not used
  as the sole or guaranteed capture opportunity. Deliberate successful replacement
  discards only the outgoing lineage. Recovery discard affects only the selected
  inactive lineage. Restore claims its existing retention slot with a fresh writer,
  retaining the checkpoint and installing all project content/preferences into an
  independent, pathless, dirty session with fresh history and no file handle.
- src/editor/recovery-discovery.ts and src/RecoveryPanel.tsx label browser entries
  without native saved-source comparisons. Invalid entries cannot replace the
  current document or prevent valid entries/fallbacks being reviewed. Current-tab
  and other-tab work have protected actions and specific guidance. The dialog
  explains origin/profile ownership, clearing/eviction/private-mode loss and the
  durable role of checked, user-owned downloaded files.
- src/FileControls.tsx updates the compact availability banner. Existing recovery
  feedback supplies errors, last successful capture and Retry without disabling
  editing, project downloads or agent export. README.md, docs/recovery-policy.md,
  docs/platform-services.md and docs/browser-lifecycle.md document the implemented
  browser contracts and unchanged native policy.

### Scope and remaining limitations

Browser recovery is origin/profile-local and may be unavailable, cleared or
browser-evicted; private sessions can remove it on close. A checkpoint may omit
edits since its capture. Downloaded .tilewright files remain the durable user-owned
copies, and a download request is not confirmation of a disk write. No new
physical-power-loss or guaranteed-persistence promise is made.

Whole-buffer capture/validation/hashing and transaction copies retain latency and
memory costs. No p95/peak-memory claim is made; the existing Vite >500 kB bundle
warning and performance-only refinement remain deferred to TW-049/TW-050.
The desktop app was built and native regressions rerun; an interactive packaged
AppKit/WKWebView session was not driven. Chromium is qualified by these tests;
Firefox/WebKit/Safari and live GitHub Pages/subpath deployment remain outside
this ticket. No dependencies or changes were added to TW-049 through TW-054.

The initial index was empty. All 42 unrelated pre-existing dirty/untracked files
