## Outcome

Make layers usable for separate terrain, walls, furniture, and other map content.

## Source and scope

**Source:** INTENT.md — Map use and meaning; INTENT.md — First-version scope; INTENT.md — Remaining implementation decisions.

**Execution order:** 13 of 54. Phase: painting.

**Prerequisite:** [wrk-20574578](wrk-20574578.md) — TW-012: Add fixed-size map creation and explicit canvas growth.

This is an intentionally sequential delivery backlog. The dependency includes earlier prerequisites transitively; complete it before starting this ticket.

Implementation details left open by INTENT.md are decisions to document, not additional confirmed user requirements.

## Work

- Choose and document a minimal conventional layer-management policy, including empty-document/default-layer and last-layer behavior.
- Implement add, rename, reorder, visibility, active-layer selection, and safe removal controls using stable IDs.
- Route content-affecting layer operations through document history and rendering notifications.

## Acceptance criteria

- [x] Terrain and buildings can be edited independently; current active layer and stack order are clear.
- [x] Renaming/reordering never loses tiles or registry associations, and hidden underlying content remains stored.
- [x] Removing a populated layer has deliberate user feedback and is undoable with its content and ordering restored.
- [x] A valid active-layer target exists after management operations; visibility behavior for drawing and selection is documented.

## Validation

- Test lifecycle and undo/redo for populated layers, including active-layer removal and reorder.
- Compare overlap rendering before/after visibility changes without destroying hidden data.

Record the implementation/decision location and actual validation evidence in this ticket before marking it done.

Acceptance evidence:

- Independent editing targets: tests edit a registered building layer over
  populated terrain using the active visible-layer target and prove every terrain
  run is unchanged. The panel explicitly labels the active row and top-to-bottom
  order. Add inserts above the active layer; up/down moves one stack position.
  Interactive painting and tile-selection tools remain their later feature
  tickets; this ticket validates their layer-target and command seams rather than
  claiming those tools are implemented.
- Data preservation: complete run and registry snapshots survive rename/reorder
  and undo/redo. Registered wall associations remain stable IDs. Visibility leaves
  every run, registry record, document version and history state unchanged. Detail
  and cached-overview WebGL pixel tests at DPR 1/2 show gold building pixels
  [177,139,77,255], green terrain [51,92,70,255] when hidden/reordered/removed, and
  restored gold after showing/undo. Underlying and hidden data remain stored.
- Safe removal: populated layers require a named confirmation explaining tile
  removal and Undo. Tests verify Cancel, Escape, focus return, and shortcut
  isolation without changing content/history. Active populated-layer removal and
  repeated undo/redo restore exact ID, name, registry associations, all occupied
  runs (including an 8x8 footprint across four visual chunks), and stack order.
  Empty-layer removal is immediate and undoable; non-active removal preserves the
  valid active target. Existing atomic history capacity rejection is retained.
- Active-layer and visibility policy: new documents have one empty visible
  `Layer 1`; the last layer cannot be removed. New layers become active. Removing
  the active layer selects the top remaining layer; undo/redo preserve an already
  valid active ID. Hidden layers can be active but are excluded from interactive
  drawing/selection targets; explicit multi-layer target filtering excludes hidden,
  missing and duplicate IDs. All layers may be hidden. Inspect/navigation are
  independent of visibility. As established in TW-007, visibility is transient;
  removal drops the hidden preference, so Undo restores the layer visible.
  These are documented implementation choices, not additional user requirements.
- Invalid/blank names, stale IDs and edge/no-op reorders leave content and redo
  intact. Creation after undo uses a fresh identity rather than reusing the
  abandoned redo layer. Ordinary tile edits still cause zero unrelated React panel
  updates in the existing profiler regression.
